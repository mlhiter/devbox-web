# Architecture

## Repository Shape

DevBox is split into v1 and v2 lines. Each line has a frontend and controller, while v2 also includes API/server and gateway services:

- `v1/frontend`: legacy Next.js frontend.
- `v1/controller`: legacy Kubernetes controller.
- `v2/frontend`: current Next.js app and route handlers.
- `v2/controller`: current Kubernetes controller.
- `v2/server`: v2 API/runtime support service.
- `v2/httpgate` and `v2/sshgate`: gateway services.
- `extensions/vscode`: shared VS Code extension.

## v2 Frontend Data Flow

The v2 frontend combines app UI and Next.js route handlers:

1. UI pages under `v2/frontend/app/[lang]/(platform)` call client APIs in `v2/frontend/api`.
2. Route handlers under `v2/frontend/app/api` authenticate requests and talk to Kubernetes, the template database, registry services, account services, and metrics.
3. Form data is converted into Kubernetes YAML by `v2/frontend/utils/json2Yaml.ts`.
4. Existing Kubernetes objects are adapted into frontend models by `v2/frontend/utils/adapt.ts`.
5. Patch payloads are generated by `v2/frontend/utils/tools.ts` and sent through `app/api/updateDevbox`.

## v2 Contract Boundaries

v2 frontend changes should preserve:

- DevBox CRD `devbox.sealos.io/v1alpha2`.
- `storageLimit` as the frontend storage limit field.
- SSHGate as the default v2 network contract where applicable.
- `mergeBaseImageTopLayer` handling for create/edit YAML generation.
- `@labring/sealos-shared-sdk` quota guard behavior in create/edit UI.

The v2 frontend wraps the Desktop SDK passed into `QuotaGuardProvider` with a
small compatibility adapter. If the customer Desktop does not declare
`account.getWorkspaceQuota` and replies with `function is not declare`, the
frontend treats workspace quota as unsupported for the session and bypasses only
the client-side quota guard. Environments with the bridge still use the shared
SDK quota dialog, and backend/Kubernetes quota enforcement remains unchanged.

## GPU Scheduling

GPU frontend logic supports two scheduler modes:

- `native`: selects nodes with `nvidia.com/gpu.product`.
- `hami`: writes the `nvidia.com/use-gputype` annotation and uses alias-defined resource keys.

GPU prices and inventory come from the `node-system/node-gpu-info` ConfigMap plus account resource price data. The frontend keeps alias metadata such as display names, icons, resource keys, product names, and node names so create/edit/detail screens can round-trip existing DevBoxes.

## RuntimeClass Routing

v2 DevBox CRs carry `spec.runtimeClassName`, and the controller copies that value into the reconciled Pod spec. The default frontend-created RuntimeClass comes from `DEVBOX_RUNTIME_CLASS_NAME`, while server-created DevBoxes use `devbox.createDefaults.runtimeClassName` from the server YAML config. Empty values fall back to `devbox-runtime`.

## ConfigMap Mounts

ConfigMap files are represented as form entries and rendered into ConfigMap volumes and volumeMounts. Editing ConfigMap content or mount paths requires a DevBox restart from the frontend flow so mounted files take effect in the workspace.

## Error Handling

Backend route handlers return structured JSON through `services/backend/response.ts`. Kubernetes quota errors are normalized to i18n keys before generic 403 permission mapping so users see resource-specific guidance.
